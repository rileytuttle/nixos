# NixOS Configuration for fw12

This repository contains my personal NixOS configuration for the fw12 (Framework laptop) host.

## Overview

This configuration is designed for a Framework laptop running NixOS with:
- KDE Plasma desktop environment
- Niri window manager (as an alternative)
- Various productivity tools and utilities
- Proper hardware support including Bluetooth, WiFi, and power management

`$HOME` to get around it. One repo, edit then rebuild.

## Building the Configuration

### Prerequisites

Make sure you have Nix installed with flakes enabled. You can check this by running:

```bash
nix --version
```

If you need to enable flakes, add the following to your `~/.config/nix/nix.conf`:

```
experimental-features = nix-command flakes
```

### Building for fw12

To build the configuration for the fw12 host, run:

```bash
nixos-rebuild switch --flake .#fw12
```

This will:
1. Build the system configuration for fw12
2. Switch to the new configuration
3. Reboot if necessary (this may take a while depending on your hardware)

### Checking and formatting

```bash
nix flake check   # builds every host: fw12, elitedesk, rt-dellpromax-24
nix fmt           # nixfmt (RFC 166 style) over the repo
```

`nix flake check` exists because `hosts/desktop.nix` sat broken for months
without anything noticing -- it imported a hardware scan that had never been
committed. A half-finished host fails here now instead of silently.

Note that flakes only see **git-tracked** files: a new `.nix` file that is
still untracked is invisible to the build and fails with a confusing "does not
exist in Git repository" error. `git add` it first.

### Building in Dry Run Mode

To test the build without actually switching:

```bash
nixos-rebuild test --flake .#fw12
```

This will build the configuration and allow you to review it before applying changes.

### Building for Development

For development purposes, you can also use:

```bash
nixos-rebuild build --flake .#fw12
```

This builds the system but doesn't switch to it.

## rt-dellpromax-24 (Ubuntu, non-NixOS)

`rt-dellpromax-24` is a work machine running Ubuntu 24 with nix as a plain package
manager — no NixOS. It is therefore a standalone home-manager config, not a
`nixosConfiguration`:

```bash
home-manager switch --flake .#rt-dellpromax-24
# if home-manager isn't on PATH yet:
nix run home-manager/master -- switch --flake .#rt-dellpromax-24
```

It reuses `home/core.nix`, `home/niri.nix` and `home/dank-material-shell.nix` from
fw12. The system layer fw12 gets from `modules/niri.nix` has no equivalent here, so:

- **niri itself is built from source**, outside nix, and installed into
  `/usr/local`. It therefore links Ubuntu's own mesa/driver stack and needs no
  nixGL wrapping. See *Installing niri* below.
- **`home/niri-generic-linux.nix`** is the stand-in for `modules/niri.nix`. It sets
  `targets.genericLinux.enable`, installs fuzzel/wl-clipboard/polkit_gnome/jq
  into the user profile, runs the polkit agent as a home-manager user service, and
  writes `~/.config/environment.d/95-nix-profile.conf` so niri's `spawn` actions can
  find `dms` and friends in `~/.nix-profile/bin` (gdm does not source `~/.profile`
  for Wayland sessions).
- **The lock screen needs `scripts/fix-nix-pam-unlock.sh` run once.** DMS's lock
  screen uses nix's linux-pam, which looks for the password helper at the NixOS path
  `/run/wrappers/bin/unix_chkpwd`. On Ubuntu that path doesn't exist, so the lock
  screen accepts your password and never unlocks. The script adds a tmpfiles rule
  that links that path to Ubuntu's `/usr/sbin/unix_chkpwd`. Nix's linux-pam also
  can't parse Ubuntu's `@include` lines, so the script writes a self-contained
  `/etc/pam.d/dankshell`, which DMS prefers over `login`.
- **`~/.config/niri/local.kdl` is deliberately unmanaged**, same as on fw12 — it's
  the hand-edited scratch file pulled in by the `include optional=true "local.kdl"`
  line at the end of `home/niri-config.kdl`. Host-specific display/output settings
  go there, never in `niri-config.kdl`, which is shared with fw12.
- **`home/kanata-generic-linux.nix`** is the stand-in for `modules/kanata.nix`.
  Same shared layout, run as a systemd **user** service. Needs one root-level
  setup step — see *Kanata* below.
- **home-manager owns `~/.bashrc`, `~/.profile` and `~/.tmux.conf`** here, because
  the host imports `home/core.nix`. Activation *fails* with "Existing file … is in
  the way" rather than clobbering Ubuntu's — move them aside before the first
  switch:

  ```bash
  for f in ~/.bashrc ~/.profile ~/.tmux.conf; do
    if [ -e "$f" ] || [ -L "$f" ]; then mv -v "$f" "$f.pre-hm"; fi
  done
  ```

  `ll`/`la` and the `dircolors` setup are carried over in
  `hosts/rt-dellpromax-24.nix`; the rest of Ubuntu's stock `.bashrc` was
  boilerplate home-manager already covers. `rebuild` is overridden there too,
  since core.nix's is `nixos-rebuild`.

### Git identity

`home/core.nix` sets every git option **except `user.email`**, which is left to
the importing host or profile — `home/default.nix` gives the personal machines
`rileytuttle@gmail.com`, and rt-dellpromax-24 deliberately gets none. On the work
machine git therefore refuses to commit until the repo has been given one:

```bash
git config user.email riley.tuttle@havocai.com
```

That refusal is the point — it's cheaper than rewriting authorship after a few
commits have gone out under the wrong address. Note `programs.git` is written to
`~/.config/git/config`, and git reads `~/.gitconfig` at *higher* precedence, so a
leftover `~/.gitconfig` will silently shadow all of it.

### Kanata

The layout in `dotfiles/kanataconfig.kbd` is shared by both hosts and contains
**no `(defcfg)` block**. That block is the host-specific half — which evdev
devices to grab — and it is generated per host by nix:

| | generated by | devices |
|---|---|---|
| fw12 (NixOS) | `modules/kanata.nix` → `services.kanata.keyboards.keyboard` | the internal i8042 keyboard, pinned |
| rt-dellpromax-24 (Ubuntu) | `home/kanata-generic-linux.nix` | none pinned → kanata auto-detects every keyboard |

Do not put `linux-dev` back in the shared `.kbd` file. It used to live there, which
pinned the layout to fw12's internal keyboard and made it unusable anywhere else.
(`modules/kanata.nix` also set `configFile`, which per the nixpkgs module replaces
the generated config wholesale — so its `devices` list was never consulted at all.)

On this host, nix can supply the binary, the config and the user unit, but **not**
the uinput plumbing: a kernel module, a udev rule and group membership, all
root-owned state outside `$HOME`. `kanata-host-setup` does that part. Run it once
after the first switch:

```bash
kanata-host-setup           # writes the udev rule, creates the uinput group,
                            # adds you to input+uinput, links the config into
                            # /etc/kanata (asks for sudo)
kanata-host-setup --check   # report what is and isn't in place, change nothing
```

It also symlinks `/etc/kanata/kanata.kbd` →
`~/.config/kanata/kanata.kbd`, which is the generated config. The home-manager
user unit passes `--cfg` explicitly and never reads it, but anything started as
root — a distro kanata package's system unit, or a bare `sudo kanata` — looks
there by default and would otherwise find nothing, since everything nix
installs for this host lives under `$HOME`. The link deliberately points at the
`~/.config` path rather than the `/nix/store` path behind it, so it keeps
working across switches and garbage collection.

Then **log out and back in** — group changes do not reach the already-running
systemd user manager — and:

```bash
systemctl --user status kanata
journalctl --user -u kanata -f
kanata --list               # which devices are grabbable
```

To pin specific devices instead of auto-detecting, put their paths in the `devices`
list at the top of `home/kanata-generic-linux.nix`, preferring stable
`/dev/input/by-id/…` or `by-path/…` names over `eventN` (that numbering changes
between boots). A bad layout fails `home-manager switch` rather than at login —
both hosts run the generated config through `kanata --check` at build time.

### Installing niri

`home/niri-config.kdl` ends with `include optional=true "local.kdl"`. Per niri's
docs, `include` landed in **niri 25.11** and the `optional=true` parameter only in
**niri 26.04** — so this config needs **niri 26.04 or newer**. No Ubuntu 24 release
ships anything close (24.04 has no niri package at all), which is why this host
builds from source rather than using apt.

`scripts/install-niri-from-source.sh` does the whole build and install. It asks for
sudo once up front, installs the apt build deps and rustup, clones to `~/src/niri`,
checks out the latest release tag, builds, and installs system-wide. It's safe to
re-run — it updates an existing checkout rather than recloning.

```bash
./scripts/install-niri-from-source.sh                # latest release tag
./scripts/install-niri-from-source.sh --ref v26.04   # a specific tag
./scripts/install-niri-from-source.sh --skip-deps    # skip apt + rustup
./scripts/install-niri-from-source.sh --help
```

It warns before building if the chosen tag is older than 26.04, and validates
`~/.config/niri/config.kdl` against the freshly built binary at the end.

It installs six files. **The `.desktop` file is the one that makes niri appear in
the gdm session picker** — gdm runs as its own user before login and cannot read
`$HOME`, so nothing in `~/.nix-profile` will ever be seen; these must go in system
paths:

| From | To |
|---|---|
| `target/release/niri` | `/usr/local/bin/` |
| `resources/niri-session` | `/usr/local/bin/` |
| `resources/niri.desktop` | `/usr/local/share/wayland-sessions/` |
| `resources/niri-portals.conf` | `/usr/local/share/xdg-desktop-portal/` |
| `resources/niri.service` | `/etc/systemd/user/` |
| `resources/niri-shutdown.target` | `/etc/systemd/user/` |

`niri.desktop` runs `niri-session`, which is what starts `niri.service` under the
systemd user manager — that's the step that makes
`~/.config/environment.d/95-nix-profile.conf` (written by
`home/niri-generic-linux.nix`) take effect, so nix-installed `dms`/`fuzzel` are on
`PATH` for niri's `spawn` actions.

After installing, restart gdm (or reboot) so it re-scans the session directory, and
validate the config before logging in:

```bash
niri --version
niri validate -c ~/.config/niri/config.kdl
```

Also install from apt (so they match the running system rather than coming from nix):
`gnome-terminal`, `wireplumber` (`wpctl`), `playerctl`, `xwayland-satellite`,
`xdg-desktop-portal-gnome`.

DMS is a Quickshell (Qt6/QML) app installed from nix, so unlike niri it *is* a
nix-linked GPU client: it links nix's libEGL, which cannot find Ubuntu's GL driver.
It therefore runs under **nixGL**, via a `~/.local/bin/dms` shim written by
`home/niri-generic-linux.nix` that shadows the real `dms` on `PATH`. The shim (not
an edit to the `spawn-at-startup` line) is what keeps `home/niri-config.kdl` shared
with fw12, which is NixOS and needs no wrapping.

The wrapper is selected by `nixGLBin` at the top of `home/niri-generic-linux.nix`.
It defaults to `nixGLIntel`, the mesa wrapper — which covers AMD too, despite the
name, and evaluates purely. On the NVIDIA proprietary driver, switch it to
`pkgs.nixgl.auto.nixGLNvidia`, which reads the running driver version at eval time
and so requires `home-manager switch --impure`.

### Troubleshooting: no top bar, no launcher

The bar *is* DMS. So is the Mod+Space launcher — `dms ipc spotlight toggle` only
talks to an already-running DMS process, it doesn't start anything, and there is no
separate spotlight package. A missing bar and a dead launcher are one symptom, not
two: DMS isn't running.

DMS is started by `spawn-at-startup "dms" "run"` in `home/niri-config.kdl`, not by
systemd (`home/dank-material-shell.nix` sets `systemd.enable = false` so it isn't
spawned twice), so when it fails it fails silently. Run the diagnostic from a
terminal *inside* the niri session:

```bash
./scripts/debug-dms-bar.sh
```

It walks the whole chain (gdm → niri-session → niri.service → environment.d PATH →
`dms run` → quickshell) and reports the first broken link. The keybinds also bisect
it for free — press them in order and stop at the first that does nothing:

| Key | Runs | Lives in | Still working means |
|---|---|---|---|
| Mod+T | `gnome-terminal` | apt, `/usr/bin` | niri is reading this config |
| Mod+D | `fuzzel` | nix, `~/.nix-profile/bin` | `PATH` reaches the nix profile |
| Mod+Space | `dms ipc spotlight` | the running DMS process | DMS is alive |

If only Mod+T works, it's `PATH`: the `environment.d` file is read when the systemd
user manager *starts*, so a `home-manager switch` made while already logged in won't
apply until a full logout/login. If Mod+D works but Mod+Space doesn't, `PATH` is fine
and DMS itself is dying — run `dms run` by hand and read its stderr.

Errors mentioning `QRhiGles2`, `Failed to create QRhi on the render thread`, or
`Failed to create graphics context for ... WlrLayershell` are the nixGL case above:
DMS is alive but cannot paint, so both the bar and the launcher vanish together.
`QT_QUICK_BACKEND=software dms run` confirms it by forcing CPU rendering.

## claude-container

Claude Code in a container, over whatever directory you are standing in:

```bash
claude-container                    # mount $PWD read-write, start claude
claude-container --ro               # mount it read-only instead
claude-container --ro ~/some/repo   # mount that, read-only
claude-container --skip-permissions # the container is the sandbox
claude-container --shell            # poke around inside instead
```

The workspace is bind-mounted at the same absolute path it has on the host, so
Claude sees what plain `claude` would see and its session and plan files line
up with the ones outside. `--help` lists the rest (extra mounts, ssh-agent
forwarding, where the container's `$HOME` lives).

The interesting part is that the container has **its own nix**, with
`/nix` on a named volume. Claude can fit itself out with whatever a task
needs, and it stays installed:

```
nix profile install nixpkgs#gcc nixpkgs#python3
```

`nixpkgs` in there is pinned to this flake's own lock, so a tool Claude
installs is the same build the host would have used and `cache.nixos.org`
already has it.

Built by `pkgs/claude-container/` (image + wrapper) and installed by
`home/claude-container.nix`, which is where per-machine defaults go --
`programs.claude-container.{runtime,stateDir,extraMounts,aliases,...}`. Both
fw12 and rt-dellpromax-24 enable it in their host files, aliased to
`claude-c`. Standalone it is just
`nix run github:rileytuttle/nixos#claude-container`.

Needs podman or docker on the host -- the one thing nix cannot supply here,
since a daemon socket or a setuid `newuidmap` has to be the host's own. fw12
has docker from `modules/docker.nix`; on rt-dellpromax-24 it is whatever
Ubuntu has (`apt install podman`, or the docker already there for balena
work).

Prefer podman where you have it: rootless podman maps container root to your
own uid, so the container owns its `/nix` *and* writes workspace files as you.
Under a rootful docker daemon the entrypoint drops to your uid instead and
chowns the store once per volume -- it works, the first run is just slower. A new image (claude-code bumped, or
anything in `pkgs/claude-container/` edited) gets a new tag and a fresh `/nix`
volume; `claude-container --prune` clears the leftovers.

## balena-plus

A wrapper around the balena CLI -- device names instead of UUIDs, an fzf picker
for fleets, and `tunnel`/`logs`/`ps` helpers. rt-dellpromax-24 gets it through
`home/balena.nix`.

Unlike everything else here it does **not** live in this repo. It is
[github:rileytuttle-havoc/balena-plus](https://github.com/rileytuttle-havoc/balena-plus),
pulled in as a flake input, because coworkers need it on machines that have
nothing to do with this config -- `curl -fsSL
https://raw.githubusercontent.com/rileytuttle-havoc/balena-plus/main/install.sh | bash`
installs nix if they have none and the wrapper either way. There is one copy of
the script, in that repo; change it there and `nix flake update balena-plus`
here.

The shared package deliberately carries no balena-cli -- it uses whatever
`balena` is on PATH, so nobody installs a second ~630MB copy of a CLI they
already have. That is why `home/balena.nix` still installs `pkgs.balena-cli`
itself.

### Sleep/Power Management

fw12 suspends, then hibernates to disk after 5 minutes asleep (`HibernateDelaySec` in `hosts/fw12.nix`).

Every sleep entry point goes through `smart-sleep suspend-then-hibernate` (`modules/smart-sleep.nix`):

- **Lid close**: handled by acpid (logind's `HandleLidSwitch` is `ignore`). Skipped when an external display is connected, or when a desktop like Plasma holds a `handle-lid-switch` inhibitor.
- **DMS power menu / idle timeout**: DMS's custom suspend/hibernate commands are pinned in `hosts/fw12.nix`. On battery it locks after 5 min idle and suspends after 10. On AC it locks after 15 and suspends after 30.

Bitwarden holds `memfd_secret()` memory, which makes the kernel refuse to hibernate. `smart-sleep` closes it before any hibernate-type sleep and sends a notification. Failures and fallbacks are logged to `journalctl -t smart-sleep`.
